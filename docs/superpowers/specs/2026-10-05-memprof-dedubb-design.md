# MemProf and DeduBB in the elide-toolchain LLVM — Design

**Date:** 2026-10-05
**Status:** Draft for review
**Builds on:** `docs/superpowers/specs/2026-10-04-universal-native-toolchain-design.md` (binding; "the base spec" below)
**Evidence:** `docs/notes/memprof-dedubb-research.md` (sources, file:line, experiments E1–E20). Claims marked *(unverified)* there are uncertain here too.

## 1. Intent

Make two LLVM features available in the bundle so downstream projects (Elide/WHIPLASH,
Bali/crema-jit, Komodo) can turn them on in their own builds:

1. **MemProf**: heap memory profiling plus memory-profile-guided optimization. Instrument
   (`-fmemory-profile`), run, merge (`llvm-profdata merge --profiled-binary`), use
   (`-fmemory-profile-use=`), then in the ThinLTO link clone allocation contexts and rewrite
   `operator new` into hot/cold-hinted calls that an allocator acts on.
2. **DeduBB**: the LCTES '26 post-link basic-block deduplication technique
   (<https://dl.acm.org/doi/10.1145/3814943.3816169>, code at
   <https://github.com/chaitanyaupp18/DeduBB>). It finds identical machine-code blocks across
   a whole linked binary and folds duplicates into jumps/calls to one master copy.

### 1.1 What "DeduBB" refers to (identification)

DeduBB is *"DeduBB: Binary Code Size Reduction via Post-Link Basic Block Deduplication"*
(Mamatha Ananda, Afarin, Gupta at UC Riverside; Tallam, Shen, Li at Google, the Propeller
authors). It is distributed as out-of-tree patches: LLVM CodeGen + lld + a Propeller tool
patch (`main`), and an alternative BOLT pass (`bolt-dedubb` branch, published today).
**Confidence: high.** The name matches exactly; it is "a patch/feature in LLVM" that
downstream builds wire in through flags; and it slots into the Propeller/BOLT tooling this
bundle already prepares for. Other candidates (BranchFolding tail merging, MachineOutliner,
BOLT/lld ICF, the abandoned D30774 SimplifyCFG block merging) are not called DeduBB and do
not match. It is **not upstream** in LLVM or in google/llvm-propeller: no PR, issue or RFC
was found.

| Patches needed | None for function. ## 3. MemProf

### 3.1 Upstream status (23.1.2)

Everything below works with no patch (research §1.1, experiments E1, E3–E7, E10, E18):
the driver flags, instrumentation passes (added by clang at `OptimizerLastEP`, so ThinLTO
pre-link builds are instrumented too, E18), `llvm-profdata` raw/YAML → indexed,
`MemProfUsePass` in the pre-link pipeline, ThinLTO summary serialization of `!memprof` /
`!callsite`, thin-link context disambiguation (`-enable-memprof-context-disambiguation`),
backend cloning (`*.memprof.N`), and the `SimplifyLibCalls` rewrite to
`_Znwm12__hot_cold_t` family calls (`-optimize-hot-cold-new`), gated by
`-supports-hot-cold-new` in the LTO link. Without that last flag, the ThinLTO backend
strips all MemProf info (`MemProfRemoveInfo`), so profiles are harmless by default. Non-LTO
builds also strip it: **MemProf hinting requires (Thin)LTO**.

Missing in the shipped bundle: the runtime (`-fmemory-profile` links fail, E2).

Limits that patches would not fix:
- Only `operator new` calls are hinted (`MemProfUse.cpp:182-205`). C `malloc` and Rust
  `__rust_alloc` sites are never hinted. Bali's C code gets nothing from heap hinting
  (static-data partitioning, §3.8, is the only C-relevant part).
- Runtime: x86_64 Linux only. Porting to aarch64 means a shadow-mapping and
  instrumentation port. Not planned.

### 3.4 The hot/cold shim (`src/mimalloc-hotcold.cc`)

Interface (exported, C++):

```cpp
enum class __hot_cold_t : uint8_t {};            // tcmalloc-compatible, global namespace
void* operator new  (size_t, __hot_cold_t);
void* operator new[](size_t, __hot_cold_t);
void* operator new  (size_t, const std::nothrow_t&, __hot_cold_t) noexcept;
void* operator new[](size_t, const std::nothrow_t&, __hot_cold_t) noexcept;
void* operator new  (size_t, std::align_val_t, __hot_cold_t);
void* operator new[](size_t, std::align_val_t, __hot_cold_t);
void* operator new  (size_t, std::align_val_t, const std::nothrow_t&, __hot_cold_t) noexcept;
void* operator new[](size_t, std::align_val_t, const std::nothrow_t&, __hot_cold_t) noexcept;
```

C API in `mimalloc-hotcold.h` (for tests and diagnostics):

```c
bool elide_hotcold_is_cold(const void* p);     // p lies in the cold arena
size_t elide_hotcold_cold_bytes(void);         // bytes handed out by the cold heap (approximate)
```

Behaviour: the cold heap is created on first use (`mi_reserve_os_memory_ex(size,
commit=false, allow_large=false, exclusive=true)` + `mi_heap_new_in_arena`; fallback
`mi_heap_new()`), published with an atomic CAS. The arena size comes from
`ELIDE_HOTCOLD_ARENA_MB` (default 256; 0 = separate heap, no arena). When the cold heap
returns NULL (arena full), the shim falls back to `::operator new`. OOM follows C++
semantics (`std::get_new_handler` loop, then `bad_alloc` or `nullptr` for nothrow).
`operator delete` stays the normal one, since `free` is mimalloc on both Linux libcs.
`__size_returning_new*` is not provided: LLVM only rewrites existing calls to it.

### 3.5 Downstream wiring: C/C++

Profiles are collected on `x86_64-unknown-linux-gnu`. Flags use the bundle's `<triple>-clang++`.

```sh
# 1) instrumented build (gnu x86_64). ThinLTO is fine here (E18) but not required.
MP_CFLAGS="-fmemory-profile -gmlt -fdebug-info-for-profiling \
  -fno-omit-frame-pointer -mno-omit-leaf-frame-pointer -fno-optimize-sibling-calls -fno-pie"
MP_LDFLAGS="-fmemory-profile -no-pie -Wl,-z,noseparate-code -Wl,--build-id"
# 2) run representative workloads; each process writes memprof.profraw.<pid> in its cwd,
#    or in <dir> given as -fmemory-profile=<dir>; override with MEMPROF_OPTIONS=log_path=<prefix>
# 3) index (needs the exact instrumented binary)
llvm-profdata merge memprof.profraw.* --profiled-binary ./app.instr -o app.memprofdata
# 4) optimized build, any triple; keep the same debug-info flags as step 1
USE_CFLAGS="-flto=thin -gmlt -fdebug-info-for-profiling -fmemory-profile-use=app.memprofdata"
USE_LDFLAGS="-flto=thin -fuse-ld=lld \
  -Wl,-mllvm,-enable-memprof-context-disambiguation \
  -Wl,-mllvm,-optimize-hot-cold-new \
  -Wl,-mllvm,-supports-hot-cold-new \
  -lmimalloc-hotcold"                      # gnu also: -lmimalloc ; musl: -static
```

Notes:
- `-fno-pie -no-pie -Wl,-z,noseparate-code -Wl,--build-id` are required in the
  instrumented binary only, by the profile reader (`llvm/docs/MemProf.md:37-40`).
- Evidence flags: `-Rpass=memprof` at compile time (matches);
  `-Wl,-mllvm,-pass-remarks=memprof-context-disambiguation` and
  `-Wl,-mllvm,-memprof-report-hinted-sizes` at link (clones, hints).
- Static libraries consumers build with `-fmemory-profile-use` carry the metadata in
  bitcode; hints happen only in the final executable's ThinLTO link.
- Caches: lld's ThinLTO cache key includes `-mllvm` strings but not profile contents, and
  compiler caches (sccache/ccache) may not hash `-fmemory-profile-use` file contents
  *(unverified for sccache)*. Name profiles by content hash (`app.<sha>.memprofdata`).
- Dynamic musl consumers: the shim links but always forwards (D8), so no segregation.

### 3.6 Downstream wiring: Rust

- rustc has no MemProf flag and never runs `MemProfUsePass` (empty `MemoryProfile` in
  `PassWrapper.cpp:713-735`). Rust allocation sites cannot be hinted at all (§3.1).
- **What works (E16):** Rust binaries that link C++ through linker-plugin LTO. The C++
  parts get cloning and hints in lld's ThinLTO link:
  ```sh
  RUSTFLAGS="-Clinker-plugin-lto -Clinker=x86_64-unknown-linux-gnu-clang++ \
    -Clink-arg=-fuse-ld=lld \
    -Clink-arg=-Wl,-mllvm,-enable-memprof-context-disambiguation \
    -Clink-arg=-Wl,-mllvm,-optimize-hot-cold-new \
    -Clink-arg=-Wl,-mllvm,-supports-hot-cold-new \
    -Clink-arg=-lmimalloc-hotcold"
  ```
  (C/C++ deps compiled with the `USE_CFLAGS` above.) Rust nightly's LLVM 23.1.1 bitcode
  is read by the bundle's 23.1.2 lld (base spec §5.3).
- Contexts that pass through Rust frames are truncated there: Rust callsites carry no
  `!callsite` metadata, so the thin link cannot clone across them.
- **Experimental instrumentation (E15):** `-Cpasses=memprof-module,function(memprof)` plus
  linking with `-Clink-arg=-fmemory-profile` (and the §3.5 instrument link flags) produces a
  usable raw profile. Set `MEMPROF_OPTIONS=log_path=<prefix>`, or the profile goes to stdout
  (no `MemProfProfileFilename` module flag from rustc). Value: correct access counts for
  memory touched by Rust code. Memory allocated by C++ but accessed only from
  *uninstrumented* code looks cold (zero accesses) and would be hinted cold: instrument
  every hot accessor, or don't trust cold hints for objects that cross into Rust.

### 3.7 GraalVM native-image

Native-image compiles Java with Graal's own code generator. LLVM-level MemProf cannot see
that code. The experimental LLVM backend is deprecated or removed in current GraalVM
*(unverified)*. Only C/C++ that native-image links (JNI libraries, static components) can
carry hints, and only if that final link is an lld ThinLTO link with the §3.5 `-mllvm`
flags. native-image drives the link through the `cc` it is given *(unverified whether extra
`-Wl,-mllvm` options survive)*. Not planned. Elide's JNI shared libraries built separately
with the bundle get the full C++ treatment.

### 3.8 Static data partitioning (optional, no build change)

`-fpartition-static-data-sections` + `-Wl,-z,keep-data-section-prefix` uses PGO and MemProf
data-access profiles to emit `.hot`/`.unlikely` data prefixes (`llvm/docs/MemProf.md:124-157`).
It applies to C as well. Documented only; not verified here.

## 4. DeduBB

### 4.1 Upstream status and patches

Not upstream. Vendored patches (base `llvm/llvm-project@333edde4e80e`, 2026-07-08, an
ancestor of `llvmorg-23.1.2`, 6 days before the 23.x branch point):

| Patch | Origin | Size | Applies to 23.1.2 | Evidence |
|---|---|---|---|---|
| `0100-dedubb-codegen.patch` | DeduBB `main` `07d730d`: `patches/llvm-project-dedubb.patch` + local gate (D10) | 4725 lines: 3 new CodeGen files (~2.6k), X86/AArch64 InstrInfo hooks, TargetPassConfig, AsmPrinter, MachineFunction, UnreachableBlockElim, lld LinkerScript (+test), clang driver CMake | clean, 1 offset | all patched TUs `-fsyntax-only` OK; patched `llc`: 6/6 DeduBB tests pass; 40 related X86 tests pass (E9) |
| `0101-dedubb-bolt.patch` | `bolt-dedubb` `0e20b1f` | 2260 lines: `bolt/lib/Passes/DeduBB.cpp` (2018 new), pass manager, RewriteInstance, X86MCPlusBuilder | clean, 1 offset | syntax OK; not built or run |
| Propeller patch (phase 2) | DeduBB `main`: `patches/llvm-propeller-dedubb.patch` | 6567 lines, mostly new files | 2 hunks fail against our pin `ddfb8b7` (base is `e2c7049`, 22 commits older) | dry run |

Risk: **medium**. The code is a research artifact (51 commits, one author, no upstream
review), but it is defensive. It checks liveness of the link register (`LiveRegUnits`,
`LivePhysRegs`), skips blocks with CFI, labels, EH pads, inline asm, red-zone functions and
stack-argument calls, and disables Save-and-Jump under IBT (`cf-protection-branch`). Inertness:
with no `-dedubb-directives` every pass returns immediately, except one unconditional
change in `UnreachableBlockElim` (address-taken unreachable blocks are kept), which D10
gates. Conflict expectation on future 23.1.x bumps: low. The touched files are stable,
and the `X86InstrInfo.cpp` insertion point (after `insertOutlinedCall`) is the only offset today.

Arch support: x86-64: Tail Call, Save-and-Jump (`%r11` link register), Call-Return, and
subsequences. AArch64: Tail Call only (`TCRETURNdi`). BOLT variant: x86-64 only. darwin:
none (no BB address maps on Mach-O, E19; BOLT is not built on darwin).

### 4.2 Build changes

- `src/patches/llvm/0100-dedubb-codegen.patch`, `0101-dedubb-bolt.patch` (D10). `apply_patches`
  in stages 10/30/40 (D1) covers them. The darwin stage 10 build also compiles the CodeGen

### 4.4 Downstream wiring

**Route A: BOLT (phase 1, x86-64 Linux):**
```sh
# final link must keep relocations
LDFLAGS="$LDFLAGS -Wl,--emit-relocs"
llvm-bolt app -o app.dedubb --dedubb            # + --dedubb-cold-only -data=perf.fdata for perf-safe folding
llvm-strip app.dedubb
```
`--dedubb` also defaults `--use-old-text --use-gnu-stack --align-functions=1`. When BOLT
must add a segment, `--use-gnu-stack` repurposes `PT_GNU_STACK`, so **the output loses its
non-executable-stack marking**. Treat that as a release blocker for anything
security-sensitive (§7). The stripped file grows (+5.6% on clang) even though `.text` shrinks.

**Route B: CodeGen (phase 2, x86-64 and aarch64 Linux, best size):**
```sh
BASE="-flto=thin -fbasic-block-address-map"   # compile
BASE_LD="-flto=thin -fuse-ld=lld -Wl,--lto-basic-block-address-map -Wl,-z,keep-text-section-prefix"
# 1) baseline build with BASE/BASE_LD  ->  app
generate_propeller_profiles --binary=app --dedubb_profile=dedubb.$(sha).txt --dedubb_subsequence
# 2) identical rebuild + directives (link step only is enough under ThinLTO; codegen happens in lld)
LDFLAGS="$BASE_LD -Wl,-mllvm,-dedubb-directives=dedubb.<sha>.txt"
```
- Under ThinLTO all codegen runs inside lld, so only the *link* needs the directives.
  Non-LTO objects need `-mllvm -dedubb-directives=…` on every compile *(not exercised)*.
- Rust: in a `-Clinker-plugin-lto` link the Rust modules are code-generated by lld and get
  BB address maps from `--lto-basic-block-address-map`, so they fold like C/C++. Non-LTO
  Rust crates can emit maps with `-Cllvm-args=-basic-block-address-map` (E17). Folding them
  also needs `-Cllvm-args=-dedubb-directives=<file>`, which only rustc's own LLVM would
  read, and rustc's LLVM is not patched: **out of scope**. Precompiled std is native code
  without maps and is left alone.
- Apply DeduBB only at a final link (executable/shared object). `DeduBB.master.N` symbols
  are global-hidden. Two separately DeduBB'd relocatable inputs would collide, so never
  ship DeduBB'd static archives (none of the bundle's archives use it).
- Both builds must be bit-identical apart from the directive flag (the directive file
  embeds master machine code as hex). ThinLTO cache: key includes the `-mllvm` string, not
  file contents; use content-hashed directive file names.
- With `-fcf-protection=branch` (parked in `cflags/labs.disabled.txt`), Save-and-Jump is
  automatically skipped. On arm64 `-mbranch-protection=standard` Tail Call folds use direct
  branches (no BTI landing pad needed) *(unverified on hardware)*.

**GraalVM:** Java code cannot pass through LLVM CodeGen. Running BOLT `--dedubb` on a
native-image ELF linked with `--emit-relocs` is conceivable but untested *(unverified)*;
not planned.

## 5. Pipeline ordering and interactions

Recommended order for a consumer that wants everything (all profiling builds are
**non-DeduBB, non-BOLT** binaries):

1. **IRPGO**: `-fprofile-generate` → run → `llvm-profdata merge` → `pgo.profdata`.
2. **MemProf profile** (gnu x86_64): instrument with `-fprofile-use=pgo.profdata
   -fmemory-profile` (allowed together), so inlining matches the final build → run →
   `merge --profiled-binary` → `mem.memprofdata`.
3. **CSPGO** (optional): `-fprofile-use=pgo.profdata -fcs-profile-generate
   -fmemory-profile-use=mem.memprofdata` (the driver only rejects `-fmemory-profile-use`
   together with `-fprofile-generate` or `-fmemory-profile`) → merge with `pgo.profdata` → `merged.profdata`.
4. **Final ThinLTO build**: `-fprofile-use=merged.profdata -fmemory-profile-use=mem.memprofdata`,
   link with the three `-mllvm` options and `-lmimalloc-hotcold`.
5. **Layout**: *either* Propeller (perf on step 4 built with `-fbasic-block-address-map`,
   `generate_propeller_profiles --cc_profile/--ld_profile`, rebuild) *or* BOLT (step 4
   linked with `--emit-relocs`, perf → `perf2bolt` → `llvm-bolt` with layout options).
6. **Size**: DeduBB last. With Propeller, the same `generate_propeller_profiles` run can
   emit the layout profiles and `--dedubb_profile --dedubb_cold_only` from one perf
   profile, so steps 5–6 share one rebuild (the `performance` branch does exactly this)
   *(not reproduced here)*. With BOLT, add `--dedubb [--dedubb-cold-only]` to the layout
   invocation *(composition with layout passes unverified)*.

Interactions:
- **MemProf × DeduBB/ICF:** MemProf clones differ at the hinted call, so ICF cannot merge
  them; DeduBB may fold their identical blocks back together. That is correct and recovers
  most of the clone size cost.
- **DeduBB × profiling:** folded code reports samples and stack frames at
  `DeduBB.master.*`, and Tail Call folds drop the caller frame. Never collect
  PGO/MemProf/Propeller profiles from a DeduBB binary.
- **CodeGen-DeduBB × BOLT:** do not stack them. Save-and-Jump masters end in `jmp *%r11`
  and have no CFI, so BOLT would mark them non-simple *(expected, unverified)*. Pick route A
  or route B.
- **MemProf × BOLT/Propeller:** independent. Both act on the step-4 binary.
- **`-fbasic-block-sections=all`** (parked cflag) is not needed: DeduBB and Propeller both
  use address maps for profiling builds.

## 7. Risks

1. **DeduBB is unreviewed research code** in the shipped compiler. Mitigation: fully inert
   without directives (D10 gate + `check_dedubb_inert`); knob to drop it; the plan builds
   and runs its lit tests once (Task 5) and a consumer-sized trial before enabling for releases.
2. **BOLT `--dedubb` drops `PT_GNU_STACK` NX marking** when it must add a segment
   (documented by the authors). Consumers must check `readelf -lW` output or pass
   `--use-gnu-stack=0` *(whether that disables the default cleanly is unverified)*.
3. **Unwinding through DeduBB masters** relies on the patch's CFI reasoning (Call-Return
   masters share one FDE per module; Save-and-Jump masters have none and contain no calls).
   Exceptions, `perf` call graphs and crash reporters that walk stacks need testing on a
   real consumer.
4. **MemProf cold misclassification** for memory accessed from uninstrumented code (Rust,
   JIT code in crema-jit, Java via JNI): looks cold, gets a cold hint, ends up in the cold
   arena. Effect is performance only, never correctness.
5. **Profile staleness**: MemProf matching uses debug line/column per function; source
   drift lowers match rates (`-memprof-salvage-stale-profile` exists, untested).
6. **Propeller build** pulls 5 third-party deps at configure time and our existing
   propeller patches are stale. Hence phase 2.
7. **Dynamic musl in the bundle appears broken** (side finding, notes §4). Unrelated to
   these features, but it rules out musl memprof runtimes for now.
8. **Bundle growth**: memprof runtimes ~5 MB (gnu x86_64 only); patched tools a few hundred KB.

## 8. Open questions for the user

1. DeduBB phase 1 via BOLT (fast, x86-64, NX caveat, file grows) or wait for the Propeller
   route (best size, aarch64 Tail Call too, needs the propeller build)? Recommendation: both, in that order.
2. Ship DeduBB patches enabled by default (inert), or only behind `LLVM_DEDUBB=yes` on
   specific release lines?
3. Is crema-jit's / Elide's C++ allocation volume through `operator new` meaningful? If
   allocations are mostly C `malloc` or Rust, MemProf hinting buys little. Static-data
   partitioning may be the only win.
4. Should `libmimalloc-hotcold` also send hot allocations to their own heap, or tune the
   cold threshold (default `hint < 128`)?
5. Which GraalVM version does Elide pin? That settles whether any LLVM-backend path is
   still possible.
6. OK to backport #222126/#208911 (changes clone choices relative to stock 23.1.2), or keep
   LLVM byte-identical to upstream apart from DeduBB?

## 9. Out of scope

- An aarch64 or darwin MemProf runtime; MemProf for musl static binaries.
- Hinting `malloc`/Rust allocations (needs LLVM and rustc work upstream).
- Patching rustc's LLVM or adding rustc flags.
- DeduBB'ing the bundle's own tools (possible later via `CLANG_DEDUBB_DIRECTIVES`).
- Upstreaming DeduBB.
